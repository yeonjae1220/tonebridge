# 파일럿 계측 등록·리허설 운영 절차

구현: V27(참여 등록 + PostgreSQL 일별 진단). 운영 활성화·참여자 연락·실기기 리허설은 별도 실행이다.
정책: [수집·보관](data-collection-policy.md) · [참여자 안내](pilot-participant-notice.md).

## 준비

1. PostgreSQL의 V27 적용과 백엔드 건강 상태를 확인한다. 로컬 H2에서는 계측 활성화를 명시적으로 거부하며, 비활성 개발 환경의 만료 작업은 PostgreSQL 전용 테이블을 조회하지 않는다. 이 마이그레이션은 기존 학습 데이터를 바꾸거나 계정을 등록하지 않는다.
2. 기존 전역 플래그 false를 유지한다. 문의·로그·백업 보관 기간과 대응 담당자/시간을 확인한다.
3. 참여자 안내를 제공하고 참여 의사를 확인한다. 실제 명단은 저장소 밖 접근 제한 경로에 보관한다.
   대상 계정을 UUID로 확인하고, 학습 보고서용 친구 쌍 명단과 리허설 계정 명단을 구분한다.
4. 대상 사용자/기존 등록을 SELECT로 미리 확인한다. 쓰기 전 백업은 exit code가 아닌 원격 파일 시각·크기로 검증한다.
5. 운영자의 안전한 DB 접속으로 `scripts/validation/enroll.sql`을 실행한다. psql 변수는 SQL에서
   리터럴 인용된다. 자격증명·참여자 값은 명령 기록/PR/CI 로그에 노출하지 않는다.

필수 변수: user_id, notice_version, acknowledged_at, starts_at, ends_at. 시각은 UTC ISO 8601이다.
파일럿 기간은 14일, 테이블 상한은 30일이다. 안내 확인 시각은 시작 시각보다 늦을 수 없다.
기존 등록이 있으면 SQL은 실패한다. 자동으로 종료 시각을 늘리지 말고 새 안내/확인 기록과 함께 검토한다.
참여 등록은 운영자 DB 작업이며 외부용 API는 없다.

## 활성화

- 리허설 A/B 두 계정을 등록하고 C는 미등록으로 둔다. 모집 전 일반 이용자의 등록은 하지 않는다.
- `k8s/backend.yaml`의 명시적 TONEBRIDGE_VALIDATION_ENABLED를 true로 변경하는 배포를 수행한다.
  같은 파일로 kubectl diff를 먼저 확인하고, 버전 관리된 변경을 배포한다. set env만으로 영구 설정하지 않는다.
  현재 매니페스트는 안전한 기본값 false다. 운영 플래그 변경은 이 구현 작업에서 실행하지 않는다.
- 백엔드 재시작 후 유효 설정과 V27, 등록 기간을 확인한다. 전역 플래그는 시작 시 읽으므로 변경 후 재시작이 필요하다.
- 공개 actuator/새 조회 API를 열지 않는다. 진단 정본은 DB이며 별도 Prometheus scrape가 없어도 보존된다.

## 리허설과 기대 결과

새 카드와 별도 검증 시작 시각을 사용한다. 읽기 전용 DB 세션에서 baseline을 기록한다.

| 실행 | 기대 결과 |
| --- | --- |
| 미등록 C의 개인 학습·진단 전송 | 학습 성공, C의 활동/진단 집계 증가 없음 |
| A만 참여한 공유 연습장에서 A/B 학습 | 학습 성공, 공유 활동 증가 없음 |
| A/B 등록 후 친구 수락 → A 예시 음성 → B 연습 → A 피드백 → B 재시도 | 정상 학습, 연결/첫 반복/피드백 학습자/재시도 학습자 각각 1 |
| A가 자신의 연습에 메모 또는 같은 피드백 수정 | 상대 피드백/학습자 분모 중복 증가 없음 |
| 미등록 계정으로 전환 중 업로드 완료 | 새 계정으로 진단·학습 확인 저장·보상 삭제·이동 없음(기존 회귀 테스트도 유지) |
| 진단 1건을 저장한 뒤 백엔드 재시작, 같은 진단 1건 저장 | DB 합계 baseline + 2. Micrometer 자체 초기화는 가능 |
| 서버가 진단을 저장하지 못함 | HTTP 503, 브라우저 학습은 계속 가능. 진단 자동 재전송 없음 |
| 참여 행 잠금 대기 중 등록 기간 만료 | 대기 해제 후 학습 활동·진단을 저장하지 않음. 기간이 여전히 유효한 경우 정상 저장 |
| A 철회와 진행 중 저장 경합 | 철회 트랜잭션 후 관련 검증 활동 없음. 이후 학습은 가능하나 공유 활동 수집 안 됨 |

```bash
# 실제 연결/명단은 운영자의 보호된 환경에서 공급한다. 예시 날짜는 모집 일정이 아니다.
PGOPTIONS='-c default_transaction_read_only=on' psql -X -v ON_ERROR_STOP=1 \
  -v cohort="$(cat /secure/pilot-cohort.json)" -v started_at='2026-11-01T00:00:00Z' \
  -f scripts/validation/report.sql
PGOPTIONS='-c default_transaction_read_only=on' psql -X -v ON_ERROR_STOP=1 \
  -v from_day='2026-11-01' -v until_day='2026-11-15' \
  -f scripts/validation/diagnostics-report.sql
```

진단은 UTC 날짜의 `[from_day, until_day)` 집계이며 같은 날짜 다른 참여자의 진단도 포함한다.
일별 누적값을 그대로 조회한다. DB 일별 total에 Prometheus increase를 적용하거나 재시작마다 차감하지 않는다.
재시도는 학습자 단위, 등록 쌍은 실제 초대한 쌍의 분모가 아니다. 2주차 결과는 실제 관찰 기간이 지난 후 판정한다.
테스트에서 시간을 과거로 구성한 성공과 실제 사용자 2주 재방문을 구분한다.

## 운영 기록과 일일 점검

모집 대장 최소 필드: 참여자/쌍 코드, 안내 버전/확인 시각, 등록 상태, 실제 초대/미가입/거절,
기기·OS·브라우저, 진행자 도움/독촉 여부, 막힌 단계, 중단 이유, 문의 접수/첫 응답/해결 시각.
연락처·UUID 대응표는 분리한다. 음성이나 학습 문장을 운영 대장에 복사하지 않는다.

매일: 학습 집계, 진단 실패/성공 추이, 요청 오류/응답 시간, MinIO 객체 수·저장 바이트,
DB 크기, 문의 미처리 수, 만료 정리 잔존을 확인한다. 운영자는 파일 내용을 열지 않고 저장소 통계를 사용한다.
정리 검증은 학습의 최소 occurred_at, 진단의 최소 day, 만료 등록 잔존 수로 확인한다.
서버 기동 후 최초 60초/이후 24시간 간격 안의 정상 지연과 정리 실패를 구분한다.

## 철회·종료·복원

- 본인 확인 후 대상 UUID의 등록과 actor/peer/공유 session 연결 활동 수를 읽기 전용 SELECT로 미리 확인한다.
  백업 검증 후 `withdraw.sql`을 user_id 변수와 함께 실행하고 활동 잔존·등록 revoked_at을 다시 조회한다.
  업데이트된 등록 잠금과 삭제는 한 트랜잭션이며 별도의 참여자 명단도 철회 상태로 맞춘다.
  공유 활동 삭제로 상대방 지표가 줄 수 있으므로 수집 종료 보고에는 그 사유를 남긴다.
- 개별 참가자의 종료 시각에 수집은 자동 중단된다. 파일럿 전체 종료 시 플래그 false로 배포한다.
  종료/철회 후에도 자동 만료 작업은 유지하며 백업 복원 시에는 수집을 끈 상태로 철회/삭제를 재적용한다.
- 중단/롤백 시 전역 수집을 먼저 끈다. V27 테이블을 역삭제하지 않는다.
  V26의 전체 계정 수집 코드로 롤백해야 한다면 반드시 플래그 false를 유지한다.

## 검증 기록

이 문서의 기대 결과는 실행 체크리스트다. 자동 테스트 결과와 실제 운영 수행 결과는 각각 기록한다.
현재 운영 활성화/모집 명단 등록/실제 문의 전송/실기기 리허설은 미실행이다.


### 2026-10-29 자동 검증 결과

- Backend 전체 139개 통과, 실패/오류/건너뜀 0. PostgreSQL 16 Testcontainers와 실제 Flyway V27 사용.
- 신규 회귀: 미등록/미시작/만료/철회/전역 비활성 제외, 공유 구성원 전체 참여,
  실제 JWT 계정 선택 및 위조 본문 ID 무시, 등록 기간 제약·중복 등록 실패,

- 웹 production build(Playwright 준비 단계), type-check, lint 통과. 모바일 도움말 렌더도 확인.

- DB 지속성은 동일 DB에 연결한 새 recorder 인스턴스로 검증했다. 실제 운영 프로세스 재시작,
  운영 DB 계측 활성화, 참여자 등록/안내 발송, 백업 만료 확인은 아직 실행하지 않았다.


### 2026-10-29 후속 리뷰 수정

- P2: 참여 행의 잠금을 기다리는 동안 등록 기간이 끝나도 대기 시작 시각의 판단으로
  학습 활동과 진단이 저장될 수 있었다. PostgreSQL statement_timestamp()는 문장 시작에 고정되어
  잠금 해제 뒤에도 갱신되지 않는 것이 원인이었다.
- 수정 전 실제 PostgreSQL에서 학습·진단 만료 경합 2건이 실패하고, 기간이 유효한 대조 2건은 통과했다.
- 참여 행을 정렬된 순서로 잠근 뒤 별도 SQL의 현재 시각으로 기간/철회를 확인하도록 수정했다.
  잠금은 저장 트랜잭션 종료까지 유지해 기존 철회 직렬화도 보존한다.
- 수정 후 백엔드 전체 143건, 브라우저·인증 회귀 86건 통과(실패/오류/건너뜀 0).
  production build 포함, 문서 링크·git diff --check도 통과. 운영 활성화·배포는 실행하지 않았다.
