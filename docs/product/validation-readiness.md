# 친구 중심 MVP: 사용자 검증 준비와 실행

기준일: 2026-10-29 · 범위: 승인한 1~3단계(문서, 구현, 자동 검증 및 내부 리허설 준비).
4단계의 외부 사용자 모집·연락·2주 실험은 아직 시작하지 않았다.
정책: [mvp-policy](mvp-policy.md) · 흐름: [user-flows](user-flows.md) · 이전 배포: [delivery-plan](delivery-plan.md)

## 목표와 범위

질문은 “친구 두 사람이 도움 없이 예시 → 연습 → 상대 피드백 → 재시도를 완료하고 다시 사용하는가?”다.
첫 검증은 모바일 웹과 기존 친구 5쌍 내외를 대상으로 한다. 개인 연습·무료 커뮤니티 요청도 회귀 범위다.
통화, 파일 가져오기, AI 분석, 결제, 네이티브 초대 연결, 앱스토어 출시를 시작 조건으로 삼지 않는다.

## 1단계: 검증 운영 기준

- 검증 진행자: 서비스 운영자. 모집 전 연락 가능한 채널과 대응 시간을 참여자에게 고지한다.
- 동의: 자발적 참여, 선택적 녹음, 공유 범위, 문의 방법, 계측 및 보관 기간을 안내한다.
- 초대 링크는 닉네임 검색만 준비한다. 요청/수락과 공유 기록 접근은 별도다.
- 친구 삭제는 새 친구 관계를 없애지만 기존 공유 연습장의 권한은 유지한다.
- 작성자 메뉴의 삭제는 숨김 처리일 수 있으며 저장소 원본의 영구 삭제와 동일하지 않다.
- /help에서 원본 삭제·공유 접근 중단·오류를 요청할 수 있다. 이메일 입력은 선택이며,
  답변이나 본인 확인이 필요한 경우 이메일 또는 기존 모집 채널을 이용한다.
- 문의 내용의 이메일·닉네임만으로 권한을 변경하지 않는다. 알려진 모집 채널/로그인 계정과
  대상 기록의 소유·참여 관계를 확인한다. 친구의 기록까지 임의로 지우지 않는다.
- 검증 진행자는 요청을 접수 → 본인/범위 확인 → 승인된 관리 절차 실행 → 확인 → 응답 순으로 처리한다.
  운영 변경은 백업/대상 SELECT/트랜잭션/변경 후 권한 재검증을 갖춘 별도 작업으로 실행한다.
  기존 발급 다운로드 URL은 만료 전까지 유효할 수 있고 다운로드한 사본은 회수할 수 없음을 안내한다.
- /help 전송 경로의 운영 수신 여부와 진행자의 실제 대응 가능 여부는 모집 전 게이트다.
  자동 테스트는 수신 서비스를 모의 처리하며 실제 문의 메시지를 보내지 않는다.

## 2단계: 기술 검증 시나리오

전용 계정 A/B와 권한 없는 C를 사용한다. 개인 계정이나 실제 학습 내용은 테스트에 사용하지 않는다.

1. A가 초대 복사 → B가 비로그인 상태로 링크 열기 → 가입/언어 설정 → B가 직접 요청 → A 수락.
2. 두 기기에서 동시에 친구 연습장 시작 → 같은 연습장에 진입. 다른 제목의 별도 연습장은 허용.
3. A가 표현+예시 녹음 → B가 듣고 연습 → A가 점수 없이 피드백 → B가 다시 녹음.
4. A/B가 재접속하여 원본 시도와 새 시도, 피드백을 확인. 역할을 바꿔 반복.
5. C로 카드 조회·연습·피드백·음성 URL 발급이 거절되는지 확인.
6. 마이크 거절→재허용, 권한 대기 중 화면 이동, 녹음 중 페이지 이동, 계정 전환을 확인.
7. 업로드 요청/파일 PUT/학습 저장 각각의 실패를 구분한다. 실패 시 재시도 가능하고 성공 전 완료 안내가 없어야 한다.
8. 친구 삭제 후 공유 기록이 남는 안내, 문의 실패 시 내용 보존, 명시적 전송 후 접수 안내를 확인한다.
9. 잔액 0의 개인/친구 학습과 텍스트·음성 커뮤니티 요청을 확인한다. 신규 거래/보상은 없어야 한다.

### 실기기 선택과 작은 체크리스트

이번에는 대형 에뮬레이터를 추가 설치하지 않는다. 기존 PC Playwright로 자동 검증하고,
iPhone 12 mini에서 Safari로 접근한다. 모바일 웹 확인에는 Mac/Xcode·스토어 배포가 필요 없다.
갤럭시가 확보되면 Chrome 버전과 OS 버전을 기록하고 같은 시나리오를 실행한다.

| 확인 | iPhone Safari | Android Chrome |
| --- | --- | --- |
| OS/브라우저 버전, 검증 URL의 배포 SHA 기록 | 대기 | 기기 확보 대기 |
| 마이크 허용/거절/다시 허용 | 대기 | 대기 |
| 예시/연습 10초 녹음, 업로드, 재접속 후 재생 | 대기 | 대기 |
| 상대 기기의 녹음 재생(iOS ↔ Android) | 대기 | 대기 |
| 녹음 중 잠금/앱 전환/복귀 | 대기 | 대기 |
| Wi-Fi 끊김 후 업로드 재시도 | 대기 | 대기 |
| 메신저 인앱 브라우저에서 초대 열기, 필요 시 Safari/Chrome에서 다시 열기 | 대기 | 대기 |
| 공유 링크 로그인/가입 복귀와 작은 화면/확대 글자 | 대기 | 대기 |

자동 결과로 위 표를 성공 처리하지 않는다. 에뮬레이터는 후속 네이티브 앱 검증 때 재검토한다.

## 3단계: 최소 측정

### 활성화와 보관

- `TONEBRIDGE_VALIDATION_ENABLED=true`인 서버에서만 활동/진단 집계를 수집한다. 기본은 false다.
- 활성화 기간에 서비스를 이용하는 계정의 해당 활동이 수집되므로 참여 안내 후 검증 기간에만 켠다.
  집계는 운영자가 별도로 보관하는 모집 쌍 목록으로 제한한다. DB 저장 단계의 모집 명단 필터는 없다.
- V26 learning_activity: FRIEND_ACCEPTED, EXAMPLE_SAVED, PRACTICE_SAVED, FEEDBACK_SAVED.
  인증된 서비스가 권한 검사와 저장을 통과한 뒤 기록하며 원 작업의 롤백에 함께 롤백한다.
- 식별 정보는 내부 UUID와 시각뿐이다. 문장/음성/파일경로/이메일/IP/토큰을 이 테이블에 넣지 않는다.
  UUID도 가명 정보로 취급한다. 일반 사용자 조회 API는 없다.
- 매일 30일보다 오래된 행을 정리하므로 실행 중인 운영 DB에서 보관 상한은 31일이다.
  수집을 끈 뒤에도 정리는 계속한다. 서버 중단 기간에는 정리도 중단되고 재시작 후 실행된다.
  탈퇴한 계정이 actor/peer인 행은 FK cascade로 삭제한다. 백업의 보관은 기존 백업 정책을 따른다.
- 문의 메시지는 기존 문의 수집 서비스로 전달되며, 이 분석 테이블/31일 정책과는 별개다.
  문의·백업의 실제 보관 정책도 모집 전에 진행자가 확인한다.
- 브라우저 진단은 고정 enum 7종만 받으며 계정별 원시 기록을 남기지 않는다.
  인증 필수, 인스턴스 전체 분당 600회 제한. 최대 7종의 Micrometer 카운터만 생성한다.
  클라이언트 보고이므로 유실·조작 가능성이 있어 결제나 정확한 비용 근거로 쓰지 않는다.

### 지표 정의와 재현

`../../scripts/validation/report.sql`을 DB의 읽기 전용 세션에서 실행한다.
`cohort`은 `[{"a":"사용자 UUID","b":"친구 UUID"}]`, `started_at`은 실험 시작 UTC 시각이다.
명단/결과 파일은 저장소 밖에 보관하며 SQL은 식별자가 아닌 집계 수와 관찰 기간 완료 여부만 반환한다.
동일 쌍의 역방향/중복 입력은 한 쌍으로 처리한다. 새 실험용 카드로 시작한다.
`registered_pairs`는 양쪽 계정 UUID가 확보된 쌍만 센다. 미가입자는 SQL에 넣을 UUID가 없으므로
이 수를 전체 모집 인원/초대 전환의 분모로 쓰지 않는다. 미가입·거절·중단을 포함한 전체 모집 쌍 수는
개인정보가 분리된 모집 대장에 기록한다.

```bash
# 자격증명은 기존 안전한 연결 방식/.pgpass 사용. 실제 명단은 저장소 밖 파일에서 읽는다.
# PGOPTIONS로 SELECT 외 변경을 거부한다. psql 변수는 SQL 안에서 리터럴 인용된다.
PGOPTIONS='-c default_transaction_read_only=on' psql -X -v ON_ERROR_STOP=1 \
  -v cohort="$(cat /secure/pilot-cohort.json)" -v started_at='2026-11-01T00:00:00Z' \
  -f scripts/validation/report.sql
```

위 시각은 실행 예시이며 모집 일정이 아니다. 시작 전 수집 활성화와 수신 증거를 확인해야 한다.
기존 친구 관계는 baseline으로 인정한다. 측정 이전의 학습·피드백을 소급 생성하지 않는다.
관계/계정 삭제로 과거 분모가 달라질 수 있으므로 종료 시 집계 숫자와 탈락 사유를 별도로 기록한다.

| 지표 | 분자 / 분모 | 해석 |
| --- | --- | --- |
| 연결 완료 | connected_pairs / 수기 모집 쌍 수 | 미가입도 포함한 모집 대장을 분모로 사용. 초대 클릭 전환율이 아님 |
| 첫 반복 완료 | first_loop_pairs / connected_pairs | 실험 첫 7일 안에 상대 예시 → 연습 → 상대 피드백 순서 |
| 재시도 | retried_learners / feedback_learners | 위 반복을 완료한 쌍별 학습자 중 14일 안에 같은 카드에서 피드백 이후 시도 |
| 다음 주 재사용 | week_two_pairs / first_loop_pairs | 8~14일에 두 사람 모두 서로 공유한 연습장에서 새 활동 |

피드백 수정은 분모를 늘리지 않고 자기 메모는 상대 피드백으로 세지 않는다.
재시도는 시간 순서로 추론하며 사용자의 동기까지 증명하지 않는다.
week_one_complete/week_two_complete가 false이면 해당 비율은 잠정치로 표시한다.
모집 목표(5쌍 중 첫 반복 4, 재시도 3, 다음 주 2)는 가설이다.
현재 SQL의 재시도 단위는 학습자이므로 목표의 “재시도한 쌍 3”은 관찰 기록으로 별도 확인한다.

### 오류와 비용

- `tonebridge_validation_client_total{event=...}`에서 녹음/업로드 시도·성공·실패를 비교한다.
  마이크 거절은 MICROPHONE_DENIED로 분리한다. 시도-성공 차이에는 이탈/유실이 포함된다.
- UPLOAD 계측은 저장소 PUT 단계다. 서명 URL 발급·학습 저장 오류는 기존 서버 HTTP 상태 지표와 대조한다.
- 집계 카운터는 서버 재시작 시 초기화되므로 Prometheus 수집 연결과 보관 설정을 실제 환경에서 확인한다.
  누적값 단순 차감 대신 관찰 기간 increase를 사용한다. 외부에 actuator를 새로 공개하지 않는다.
- 매일 실제 MinIO 객체 수/저장 바이트 증가와 요청 실패, DB 활동 행 수를 기록한다.
  운영 담당자가 파일 내용을 읽지 않고 저장소 통계/관리 도구로 확인한다.
- 서버 multipart 기본 제한은 100MB, ingress 경로 제한은 110m다. presigned PUT는 서버 multipart를
  거치지 않으므로 이를 파일 검증으로 주장하지 않는다. 기존 저장소 URL 발급 rate limit은 유지한다.
- 초기 리허설에서는 10~30초 음성만 사용한다. 사용자별 저장량 상한/미참조 업로드 정리/파일 실체 검증은
  모집 확대 전 보완 사항이다. 현재 무료 정책이 저장소 무제한 보장을 뜻하지 않는다.

## 추가 리뷰와 수정 (2026-10-29)

- P1 계정 전환: 이전 요청의 401 재전송과 refresh 성공/실패가 새 계정에 영향을 줄 수 있었다.
  요청/응답의 세션 세대를 검사하고 refresh를 세션별로 공유·취소한다. 로그아웃은 로컬 상태를 즉시
  무효화하며, 쿠키 삭제 완료 전에 새 비밀번호 로그인/가입을 보내지 않는다. 초기 복원/늦은 로그인도 보호한다.
- P2 연습장 선택: 클라이언트는 최신 연습장을, 서버는 가장 오래된 연습장을 선택했다.
  목록을 생성 시각·ID 내림차순으로 고정하고 서버 재사용도 같은 첫 항목을 택한다.
- 수정 전 인증 경합 6개와 PostgreSQL 연습장 선택 1개가 실패하는 것을 확인했다.
  인증 회귀는 정상 동시 갱신·초기 복원·쿠키 정리 순서까지 11개 시나리오로 확장했다.
- 인증 문서의 예전 /api/v1 경로·refresh 함수명·미들웨어 위치도 실제 코드와 맞췄다.

## P1 후속 수정과 쿠키·업로드 회귀 (2026-10-29)

- 로그인/가입 요청이 화면 이동 뒤에도 살아 있어 늦은 `Set-Cookie`가 새 계정의 refresh 쿠키를 덮는 문제가 있었다.
  공통 인증 요청에 AbortController를 연결하고 화면 이탈·새 인증 시도·세션 변경 시 취소한다.
  로그인 중 기존 refresh를 취소해도 새 로그인을 로그아웃시키지 않으며, 이전 화면의 완료 후 이동도 차단한다.
- `/request`의 직접 파일 PUT 뒤 확인 저장에 계정 보호가 누락되어 있었다. 전체 생성 흐름에 시작 세대를 보관하고
  각 비동기 단계 사이와 저장·실패 시 삭제·성공/실패 UI 반영 전에 검사한다. 이전 업로드의 완료 진단도 새 계정으로 보내지 않는다.
  이미 이전 계정으로 만들어진 카드/파일을 다른 계정 권한으로 정리하지 않는다. 서버에 도착한 작업의 롤백을 보장하는 기능은 아니다.
- 수정 전 새 브라우저 테스트 8개 중 쿠키 경합 4개와 계정 전환 업로드 2개가 실패하고, 같은 계정 정상/실패 2개는 통과했다.
- 새 브라우저 테스트는 로그인→로그인, 로그인→가입, 가입→로그인, 가입→가입의 늦은 응답 뒤
  브라우저 HttpOnly 쿠키의 값·Path 및 새로고침 후 복원 계정을 검사한다. 저장소 PUT 성공/실패 각각에 대해
  계정 전환 뒤 확인 저장·보상 삭제·진단 POST·화면 이동이 없는지 검사하고 같은 계정의 정상 처리를 대조한다.
- 인증 클라이언트 테스트는 기존 refresh 취소와 새 로그인 경합, 화면 정리 없이 새 가입이 이전 로그인을 취소하는 경우,
  이미 취소된 인증 시도에 HTTP 요청이 발생하지 않는 경우를 추가한다.
- 최종 전체 Playwright 86개, production build, type-check, lint, git diff --check가 통과했다.
  이번 P1 수정은 프론트엔드에 한정되며 백엔드/Flutter 코드는 추가 변경하지 않았다.
- API·저장소 응답과 마이크는 테스트 fixture다. 실제 운영 계정 생성·메시지 전송이나 실기기 검증은 수행하지 않는다.
